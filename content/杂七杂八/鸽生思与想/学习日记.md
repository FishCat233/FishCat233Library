然后晚些时候把 git 清理了一下，网上的教程也是太繁杂了，甚至连 UserSettings 这种东西都加进 git，在我看了文件内容后感觉这种界面设置应该不用加进 git，所以又加进 .gitignore 然后删除追踪了。我还特别记了一下命令，因为每次都忘。

```bash
git rm -r --chace # -r 是递归文件夹 --chache 是只删除缓存而不是实际文件
git add . # 删除后再将所有文件添加进追踪，原来没在 .gitignore 的加进缓存区四舍五入就是没更改，而后进 .gitignore 的则没被添加进缓存区，所以会被在追踪列表判定为删除更改。
git commit -m "clean track files but in .gitignore" # 英语不好，这里是 commit 的信息
```

赶时间复习考试完以后我把这事给忘了，或者说从年初起就没怎么写笔记。现在寒假快结束了才想起来。

不过问题不大，寒假期间还是有学东西的，虽然和寒假前的计划完全不一样：和人合作做一个完整的多人2D横版物块破坏游戏，并且有完整的功能甚至更多联机功能，同时还补图形学和Shader知识，如果有空可以尝试写 Minecraft 光影。

现在看来当时犯了个经典错误，忽视了人的生产力是有限的这一个事实。想要通过意志力强撑是完全不行的，在有充足动机的情况下心理上想要行动是简单的，但是精神上思考的疲惫确实真实的，所以并不能靠意志严格高效用光每一点时间。这点是我在前几天琢磨的时候才领会到的。

下面的话是之间从今天的笔记里面写的，我觉得这些话能体现我这阵子关于编码的新理解，虽然我也不知道是否是多余。

> 实际上光是受击反馈就从19点搞到20点半了。搞这么慢的原因还是在于没有完全跟教程走，而是慢吞吞去研究如何写会比较舒服和优质。
> 
> 比如说花了些时间研究基于领域的匈牙利式命名，比如说引起资源命名使用领域缩写来命名，例如 Hitbox 的碰撞层命名成 `HB_Ally` 和 `HB_Hostile`。我个人认为，虽然这种命名方法看着有些诡异和小团体，但实际上对互相熟悉的团队或者说个人多天以后再看来认知负担会比较小。
> 
> 另一个研究则是关于 Hitbox / Hurtbox 的设计。Hitbox 和 Hurtbox 实际上都是不同 GameObject 之间的例外，因此应用了之前的依赖规则使用了 SerializeField 和 LogError 直接提示，对同物体间的组件之间的组件要求 RequireComponent。这一套下来我在添加组件的时候心智负担小了不少，我都不用思考代码底层具体怎么样也能整理清楚依赖关系，可以说我之前设计的品味规则实际上是对可维护性这块有效果的。
> 
> 而 Hitbox / Hurtbox 设计上我也再次体会到设计模式和代码结构实际上都是一场赌，如果你未来用得到某个功能你就可以提前做好准备，否则不论什么状态都会或是容易或是不容易两种方向的改变存在。设计模式实际上是中庸之道，在未来和现在之间根据你的显示需求获得中庸的结果就可以了，不论怎么写的不会变好。*不过我肯定的是，简洁的架构对可维护性好，而可维护性其实才是代码能够持续开发的根本，对于长期修改的软件来说，持续使用和持续开发等同密切相关。因此可维护性是代码能够持续开发的根本。*
> 
> 走一步想一步还是慢，不过我希望前期这样思考，能够积累足够的经验，提高以后的开发速度，尤其是重构和添加新功能时思考的速度。
